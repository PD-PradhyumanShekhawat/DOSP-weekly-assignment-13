# Assignment 13 Report

## HMAC-Based API Request Authentication

### Overview

This assignment implements a small API request-authentication simulator using HMAC-SHA256. The client and server share a secret. The client calculates an HMAC over the complete request context, and the server calculates the expected HMAC independently. A request is accepted only when the HMAC is valid and the request also passes freshness, replay, and rate-limit checks.

### Request Authentication

The authenticated request contains a client ID, method, path, timestamp, nonce, and body. Every field is included in the MAC input. Variable-length fields are length-prefixed before concatenation to avoid ambiguous encodings. The HMAC is generated with `crypto:mac/4`, and the result is compared with `crypto:hash_equals/2`.

### Replay Protection and Freshness

Each request receives a fresh 16-byte nonce generated by `crypto:strong_rand_bytes/1`. The server checks that the timestamp is within the configured time window. After a valid request is accepted, the server records the client ID and nonce. A later request with that same client/nonce pair is rejected. Expired nonce records are pruned as later requests are processed.

### Rate Limiting

The server maintains a fixed-window request counter for each registered client. Every well-formed request from a registered client counts, including requests with an invalid HMAC. Once the configured request limit is reached, subsequent attempts are rejected until the window expires. This demonstrates why HMAC verification should be paired with rate limiting rather than assuming that a fast cryptographic check alone prevents guessing attacks.

### Limitations

This is a local simulator, not a network service. It does not implement HTTP parsing, TLS, persistent storage, distributed rate-limit coordination, or secure provisioning/rotation of shared secrets. Its state is passed explicitly between Erlang function calls, so a production service would need reliable shared storage or another coordinated mechanism when deployed across multiple nodes. HMAC uses a shared secret; unlike a public-key signature, it does not provide non-repudiation.

### Conclusion

The project demonstrates how HMAC-SHA256 can authenticate API requests and protect request integrity, and why timestamps, unique nonces, and rate limiting are needed alongside MAC verification.
